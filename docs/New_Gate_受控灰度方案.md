# New Gate 受控灰度方案（草稿 v0.1）

> 目的：申请公网发布前的**受控**灰度。核心不是「能扛多少」，而是「超限时怎么死得干净」。
> 本文所有数字都对应 `workbench/serve_parser.py` 里真实存在的开关，不是设想值。

## 0. 一句话立场

单件 50 MB、并发 2、解析 180 秒强杀、失败一律显式返回状态码而非静默降级。
宁可拒绝，不产出半份结果。

## 1. 实测基线（本机，非服务器）

| 项 | 实测值 | 备注 |
| --- | --- | --- |
| 样本 | V101 / CD74HCT574 | 21 页、14 张表、1,224,626 B |
| 解析耗时 | **16.8 s / 22.3 s**（两次） | 含子进程启动与产物落盘 |
| 响应体 | 2,669,609 B | `parser_output` 含 text_blocks / tables / candidates(1448) |
| 渲染页 | 11 / 21 页 | 仅检测到表格的页才渲染 PNG |
| 红框候选 | 54 处（第 1 页） | `page_number + bbox`（PDF 点坐标） |

180 秒预算 ÷ 22 秒 ≈ **8 倍余量**。这是「正常件不会撞超时」的依据；
但**没有**做 200 页级大件的实测，见 §8。

## 2. 三道上传闸门（50 MB）

| 闸门 | 时机 | 行为 |
| --- | --- | --- |
| 1. 声明长度 | 读到 `Content-Length` 时 | 超限直接 HTTP 413，**不读 body** |
| 2. 流式累计 | 分块读取过程中 | 累计超限立即中断连接并 413，**不落盘** |
| 3. 兜底复检 | body 读完后 | 再次比较长度，防声明值撒谎 |

上限由 `ICEX_MAX_UPLOAD_MB` 控制，**默认 50**（原硬编码 80 MiB 已改为可配，
灰度期设 50，内部联调可临时抬到 80，不必改源码）。

落盘路径由服务端生成：`uploads/<request_id>/<uuid4>.pdf`，用户提交的文件名只进
metadata、不参与路径拼接，落盘前还有一次 `is_relative_to()` 越界断言。

> 未做：压缩包、加密 PDF、损坏 PDF 的差异化话术。当前统一由 `validate_pdf()`
> 返回「缺少 %PDF 魔数」或解析失败状态。

## 3. 并发与排队

| 项 | 值 | 机制 |
| --- | --- | --- |
| 解析并发 | **2** | `asyncio.Semaphore`，`ICEX_WORKBENCH_MAX_CONCURRENCY` |
| 分类超时 | 45 s | 独立子进程，`ICEX_CLASSIFY_TIMEOUT` |
| 解析超时 | **180 s** | 独立子进程，`ICEX_PARSE_TIMEOUT` |

为什么是 2：解析是 CPU 密集的单进程，一台 2 vCPU 机器上开 3 个只会互相拖慢，
把 22 秒拖成 60 秒，反而更容易撞超时。**并发数应等于 vCPU 数，不是越大越好。**

排队策略（需在网关层落实，应用层不做队列）：
- 超出并发的请求在网关**排队**，队列深度上限 20；
- 排队等待超过 30 s 直接返回 429 + `Retry-After`，不让请求在服务里无限堆积；
- 应用层不实现重试，重试由客户端决定，避免雪崩式重放。

> 当前代码只有信号量，**没有队列深度与 429**。这两项必须在网关（Nginx / Cloudflare）
> 或加一层中间件实现，属于灰度前必做项。

## 4. 180 秒强杀

不是「等它自己超时」，是**主动杀进程组**：

1. 解析在独立子进程执行（`asyncio.create_subprocess_exec`），父进程只读 stdout 哨兵；
2. 超时后 `terminate()` → 宽限 5 s → `kill()`，确保子进程及其子进程一起死；
3. 返回 `PARSE_TIMEOUT`，附 `worker_kind`、已发生的 `parse_pdf_calls` 次数；
4. **不重试**。超时即失败，由客户端决定是否重提。

关键点：`parse_pdf_calls` 用 `PARSER_CALL_ENTERED` 阶段标记统计，崩溃/超时时
已发生的调用不会被错记成 0——否则监控会显示「没调用过却超时了」。

## 5. 冻结闸门（默认关闭）

`ICEX_WORKBENCH_ALLOW_PARSE` 默认 `0`。为 0 时 `/api/parse` 与 `/api/process`
**不读请求体、不落盘、不启动 worker**，直接返回 `FROZEN`。

灰度期建议：保留这个闸门作为**总开关**，出问题时置 0 即可全量止血，
不需要回滚代码。这比「重新部署上一版」快得多。

## 6. 观测指标（灰度必须有的 6 个）

| 指标 | 用途 | 告警阈值（建议） |
| --- | --- | --- |
| 请求成功率 | 分母含 4xx/5xx | < 95% 持续 5 min |
| P95 解析耗时 | 撞超时的前兆 | > 90 s |
| 413 比例 | 50 MB 是否卡太紧 | > 5% 说明该放宽或加前端提示 |
| 429 比例 | 并发是否不够 | > 10% 说明该扩容 |
| 超时率 | 强杀频率 | > 1% |
| 单进程峰值 RSS | 决定单机可承载并发 | 接近机器内存 70% |

> 峰值 RSS 目前**没有测**。这是灰度前必须补的一项：50 MB 的 PDF 渲染成
> 150 dpi PNG 后，内存可能远大于文件本身。

## 7. 回滚与熔断

| 场景 | 动作 | 恢复时间 |
| --- | --- | --- |
| 错误率突增 | `ICEX_WORKBENCH_ALLOW_PARSE=0` 全量止血 | 秒级（改环境变量重启） |
| 单机资源打满 | 网关摘除该节点，保留 1 台承接 | 分钟级 |
| 产物异常（错行/错值） | 关闸 + 保留 run 目录取证，不回滚产物 | 视排查 |

所有 run 落盘在 `runs/<run_id>/`，**失败也保留**（含 diagnostics 与阶段标记），
这是事后定位的唯一依据。清理策略：灰度期不自动清理，人工按月归档。

## 8. 明确没验证的事（不要对外声称）

1. **没有 DO 服务器实测**。本文所有数字来自本机 Windows + `127.0.0.1:8000`。
2. **没有测大件**。50 MB / 200 页级的耗时与内存未知；22 秒只是 1.2 MB / 21 页。
3. **没有测并发**。并发 2 是设计值，未做压测，未测排队与 429。
4. **没有队列与 429 的实现**。当前只有信号量，网关层限流是待做项。
5. **没有公网暴露过**。TLS、鉴权、防刷、上传体积之外的滥用面均未评估。

## 9. 灰度阶梯（建议）

| 阶段 | 开放范围 | 并发 | 观察期 | 放行条件 |
| --- | --- | --- | --- | --- |
| G0 | 内网 / 白名单 5 人 | 2 | 3 天 | 成功率 ≥ 99%，无超时 |
| G1 | 邀请制 50 人 | 2 | 1 周 | P95 < 60 s，413 < 5% |
| G2 | 公开但限流（10 rpm/IP） | 4 | 2 周 | 429 < 10%，RSS < 70% |
| G3 | 公开 | 按 vCPU 扩 | — | 视 G2 数据决定 |

每一阶的**退出条件**是上一阶的观测数据，不是时间到了就升。

附：本文引用的开关

```bash
ICEX_WORKBENCH_ALLOW_PARSE=1     # 总闸，0 = 全部 FROZEN
ICEX_MAX_UPLOAD_MB=50            # 单件上限
ICEX_PARSE_TIMEOUT=180           # 解析强杀秒数
ICEX_CLASSIFY_TIMEOUT=45         # 分类超时
ICEX_WORKBENCH_MAX_CONCURRENCY=2 # 解析并发（= vCPU 数）
```
