# evaluator v3：一对一消费匹配

本文件说明 v3 评估器相对 v2 改了什么、怎么证明改对了、以及为什么这些改动没有牵连其他数字。

> 一句话：**Parser 没重跑，只重算了评估器侧。** 输入是 v2 冻结的
> `runs/gate6a_replay_v2_postfix/per_sample/<sno>/{tables.json, candidates.json}`。

---

## 1. 先证「没换输入」：块组装零漂移

在动匹配逻辑之前，先证明用冻结产物重建出来的候选块与 v2 逐块相同。
否则后面所有的数字变化都无法归因。

`../_verify_v3_faithful.py` 做三件事：

1. 用 v2 的 `build_blocks()` 从冻结的 `tables.json`／`candidates.json` 重建块；
2. 与 v2 冻结的 `per_sample_json/<sno>.json` 里的 `param_blocks` 逐块比对
   `block_id` / `symbols` / `numbers` / `n_rows` / `text` / `cond_source` / `table_units`；
3. 再用**旧匹配逻辑**跑一遍，看能否精确复现 v2 的 `104 / 89 / 8 / 7`。

实跑结果：

```
比对样本数 : 24
结果       : 全部一致
Gold 行数            重算 105   v2 冻结 105       OK
定位(hit_rows)       重算 104   v2 冻结 104       OK
exact_rows           重算 89    v2 冻结 89        OK
coarse_hits          重算 8     v2 冻结 8         OK
coarse 且完全一致        7     （v2 未单列，本次新算）
```

**基线成立。** 因此 v3 之后出现的任何数值变化，只能来自「一对一消费」这一项改动。

## 2. 算法

### 2.1 候选单位从「块」下沉到「(块, 物理行)」

v2 的块是**父块**：以有符号的行为起点，吞并其后最多 8 行，数值取并集。
一条 Gold 行「命中某块」之后，无从知道它落在块里的哪一行 —— 这正是假一对一能藏住的地方。

v3 在 `build_blocks()` 里为每个块保留 `rows_detail`：

```json
{"row_id": "p013-t01-r04", "text": "...", "numbers": [...],
 "units": [...], "symbols": [...]}
```

于是「块」只是候选的上界，「物理行」才是真正的分配单位。

### 2.2 分配顺序

```
1. tier 小的先：页内符号命中 (1) → 页外符号命中 (2) → 按值兜底 (3/4)
2. 同 tier 内，「有某个物理行能完整覆盖其数值」的先
3. 再按候选数少的先（最少剩余值启发式）
4. 最后按文档顺序兜底
```

每条 Gold 行按上述顺序取第一个**未被占用**的 (块, 行) 对，取到即占用，永不释放。

为什么第 2 条必要：V077 的 RVDD 块跨 2 行，一行是 456 MHz 那组值、一行是 I/O 电压那组值。
若先按块分配再挑行，先到的 Gold 行会盲占首行，把真正含其数值的行挤掉 ——
早期草稿确实踩了这个坑，硬命中凭空少 1。

### 2.3 condition 不参与分配

Gold 的 `condition` 是**参考字段**。拿它去挑物理行等于用答案选答案，
所以分配阶段完全不读它。分配完成后可以回头检验「被指派的物理行与 condition 是否自洽」，
那是事后佐证，不是输入。

V256 就是一个干净的例证：五条 Gold 行仅靠符号/数值证据分配，
事后检查发现各自落到的物理行与条件逐一吻合（见 §3.2）。

## 3. v2 → v3 的实际差异

### 3.1 只有 1 行改了块归属，其余 104 行完全不变

基准是 v2 冻结的 `artifacts/v2_eval_detail.csv`，逐行比对 `matched_block_id`：

```
V256/G090  p013-t01-r03 → p013-t01-r04    消费冲突，顺位到下一个物理行
```

其余 104 行的块归属、物理行、字段级判定全部与 v2 一致
（`metrics.json` → `matching.rows_differing_from_v2 = 1`，`rows_lost_vs_v2 = 0`）。

完整变动记录见 [`consumption_reassignments.csv`](consumption_reassignments.csv)，全文只此一行。

需要说明的是：**「1 行变动」不等于「一对一消费只影响 1 行」**。
v2 的 `eval_detail` 只记到块（`matched_block_id`），13 个共用父块里的 Gold 行
在 v2 中没有任何物理行归属可继承，所以 v3 补记 `matched_physical_row_id` 属于
**新增信息**，不是「改动」。上表统计的是**块 ID 层面真正变了的那一行**。

**归因分布一字未改**：`完全一致 89 / 数值错 6 / symbol 错配 5 / page 错 3 / 单位错 1 / 漏提 1`。
这说明一对一消费只修正了「谁占哪一行」，没有改变任何字段级判定。

### 3.2 V256：五条 Gold 行落到五个不同物理行

| Gold 行 | Gold 条件 | v2 命中块 | v3 物理行 | 该行文本里的条件 |
| --- | --- | --- | --- | --- |
| G088 | `TA=25°C` | `r02` | `r02` | `2V<VCELL<4.5V; TA=25°C` |
| G089 | `-20°C<TA<65°C` | `r03` | `r03` | `-20°C<TA<65°C` |
| G090 | `-40°C<TA<105°C` | `r03` ⚠ 共用 | `r04` | `-40°C<TA<105°C` |
| G091 | `-40°C<TA<125°C` | `r05` | `r05` | `-40°C<TA<125°C` |
| G092 | `1V<VCELL<5V; -40°C<TA<125°C` | `r06` | `r06` | `1V<VCELL<5V; -40°C<TA<125°C` |

⚠ 是 v2 的缺陷：G089 与 G090 值完全相同（`-7.8 / 6.6`），独立扫描时 `max()`
取第一个最大项，两行都落在单行块 `r03` 上。

修复后，**分配过程没有用 condition**，但五条行落到的物理行与各自条件恰好逐一吻合 ——
因为 r03/r04/r05/r06 的文本本身就分别写着 `-20~65`、`-40~105`、`-40~125`、`1V~5V`。
这是「一对一」把真实结构还原出来的副产品，不是调参调出来的。

### 3.3 影响面

| 项 | v2 | v3 |
| --- | --- | --- |
| 被多条 Gold 行共用的父块 | 14 | **13** |
| 其中「多行必落同一物理行」的 | 1（V256 `p013-t01-r03`，`block_rows=1`） | **0** |
| 占用物理行总数 | 未记录 | 104 = 定位数 |
| 因消费冲突丢失的定位 | — | **0** |

v2 的 14 个共用父块里，只有 V256 的 `p013-t01-r03` 是单行块（`block_rows = 1`），
两行 Gold 必然压在**同一条物理行**上，这是可以从 v2 产物直接判定的硬缺陷。
其余 13 个块的块内行数是 2~8（V011 `r04` = 3 行、V101 `r10` = 6 行、V304 `r02` = 8 行 ……），
v2 不记物理行，因此**无法从 v2 产物判定这些行是否落在同一子行** —— 这正是 v3 必须补
`matched_physical_row_id` 的理由：让「有没有共用子行」变成可验证的事实，而不是推测。

v3 把 104 条定位全部下沉到物理行后，13 个共用父块无一行重复，
逐条见 [`parent_block_sharing.csv`](parent_block_sharing.csv)（`all_distinct` 列全为 `True`），
并由 `_assert_v3_1to1.py` 的「物理行占用唯一」组断言兜底。

## 4. 硬/软分离

`coarse` 判据沿用 v2：命中块跨度 ≥ 5 行，且不是 `token` 级匹配。

```
全字段一致（值/单位/符号/页码）  89
  ├─ coarse=否 → 严格命中         82
  └─ coarse=是 → 软命中            7
```

7 条软命中的共同特征：

| 样本/行 | 符号 | 父块行数 | 匹配方式 |
| --- | --- | --- | --- |
| V111/G022 | VDD | 5 | text |
| V111/G024 | VOS | 8 | text |
| V173/G042 | Tstg | 6 | text |
| V173/G043 | IO | 6 | text |
| V304/G029 | VCC | 8 | text |
| V304/G030 | TJ | 8 | text |
| V304/G031 | IIK | 8 | text |

它们不是「算错了」，而是「值确实在解析结果里，但落在一个跨 5~8 行的大块内，
无法逐行确认」。v2 把它们直接算进完全一致，等于用大块并集冒充逐行证据。
逐条明细见 [`soft_hits.csv`](soft_hits.csv)。

## 5. 可执行的校验

两个脚本都可以直接跑，任何一个失败即非零退出：

```bash
# 忠实性：冻结产物能重建 v2 的全部指标
python workbench/gate6a_replay/_verify_v3_faithful.py

# v3 不变量：27 项断言
python workbench/gate6a_replay/_assert_v3_1to1.py
```

`_assert_v3_1to1.py` 守的 27 条里，与本次两条指控直接相关的是：

| # | 断言 | 实测 |
| --- | --- | --- |
| 1 | 严格 + 软 = 全字段一致 | 82 + 7 = 89 |
| 2 | `exact_rows` 就是严格命中 | 82 |
| 3 | 严格命中里没有 `coarse` 行 | 0 行 |
| 4 | 同一行不同时是严格与软命中 | 0 行 |
| 5 | 软命中必为 `coarse` | 0 例外 |
| 6 | 同一物理行不被两条 Gold 行占用 | 0 个重复 |
| 7 | 占用物理行数 = 定位数 | 104 = 104 |
| 8 | `matched_physical_row_id` 落在父块覆盖行内 | 0 例外 |
| 9 | 共用父块无重复物理行 | 13 个父块全部通过 |
| 10 | 严格命中的值都落在被指派的物理行上 | 82 / 82 |

第 10 条是额外收紧的：`row_verified_hit_rows = 82`，与严格命中数相等，
说明**每一条严格命中都不是「靠块并集撑起来的」**，其数值确实在被指派的那一行上。

## 6. 可复现性

审计产物必须逐字节可复现，否则哈希对比没有意义。v3 修了一个 v1/v2 遗留的缺陷：

- 早期把 `symbols`／`units` 这类 `set` 直接写进 CSV，而字符串集合的迭代顺序受
  `PYTHONHASHSEED` 随机化影响 —— 同一份数据两次运行会得到不同的元素顺序
  （实测 v1 的 `rows_parser.csv` 有 7485 行顺序不同、内容相同）。
- v3 改为 `_setrepr()` 排序输出，外观与 set 字面量一致但有序。

验证：用两个不同的 `PYTHONHASHSEED` 各跑一遍，六个产物文件 sha256 全部相同。

### 6.1 行尾：让「字节一致」在跨平台时也成立

`workbench/gate6a_replay/.gitattributes` 把 `audit/**` 与 `artifacts/**` 标为 `-text`，
禁止 git 转换行尾。不加这一条会怎样？本包 v2 就是反例：31 个文件的工作区字节（CRLF）
与提交树字节（LF）不同，而 `SHA256SUMS.txt` 记的是工作区那份 —— 在 Linux 上克隆后
执行 `sha256sum -c` 会直接报 31 个 FAILED，校验表形同废纸。

现在两侧统一为 LF，`sha256sum -c SHA256SUMS.txt` 在 Windows / Linux / macOS
以及 GitHub 的 zip 包上都应全部通过。清单本身由 `../_make_sha256sums.py` 生成，
可随时重算。
